## Контекст

Критерий: интеграционный тест нужен там, где риск живёт на стыке с внешней системой, чей контракт может поплыть от версии к версии. Мок здесь не помогает — он проверит нашу веру в контракт, а не сам контракт. В проекте таких стыков три:

1. **Qdrant**: `hybridSearch` с `prefetch` + `fusion: rrf`, именованные dense+sparse векторы, payload-индексы, параметры коллекции — контракт, который трогают Task 05 (REST→gRPC) и Task 13 (алиасы)
2. **Redis-локи + BullMQ Flows**: поведение возникает из взаимодействия (сериализация джобов, Lua-освобождение, TTL, порядок parent/children) — моком не проверить осмысленно
3. **Полный цикл** вебхук → 202 → воркер → ревью: страховочная сетка для рефакторинга (Task 12/14)

## Объём работ

### 1. Инфраструктура

- `docker-compose.test.yml`: только `qdrant` + `redis` (без Ollama/app)
- Скрипт `test:integration`: поднять compose → прогнать тесты → снести
- Отдельный glob `*.int.test.ts` (свой vitest-конфиг или workspace) — обычный `npm test` остаётся быстрым и без Docker
- Каждый тест создаёт коллекцию/очередь с уникальным именем и чистит за собой — параллельность без конфликтов

### 2. Контракт с Qdrant

- `ensureCollection`: именованные векторы (dense 768 + sparse bm25), payload-индексы создаются
- `hybridSearch`: prefetch dense+BM25 с `fusion: rrf` на реальном сервере возвращает ожидаемый порядок релевантности
- `upsert` с named vectors + sparse, `scroll` с фильтрами, `setPayload` / `delete` по фильтру
- Этот набор = автоматизированный spike Task 05: при миграции на gRPC тесты становятся регрессией (parity подтверждён, если тесты зелёные на новом клиенте)
- Алиасы (`resolveCollections` / `switchAlias`, прозрачность поиска по алиасу) — добавить с реализацией Task 13

### 3. Локи и Flows (после Task 14)

- Две джобы одного репо сериуются локом; двух разных репо — идут параллельно
- Lua-освобождение не снимает чужой лок
- Истечение TTL лока посреди джобы не приводит к гонке
- Flows: parent-джоба стартует только после завершения всех children (шов blue-green)
- `LockConflictError` → джоба повторяется, а не умирает

### 4. Smoke: вебхук → воркер → ревью

- Моки: GitHub API (diff/файлы/публикация ревью) и LLM-транспорт (фейковая стратегия)
- Настоящие: Qdrant, Redis, BullMQ, Express-приложение
- Сценарий: POST вебхука (fixture из Task 07) → 202 → воркер выполняет analyze-pr → assert: ревью опубликовано с ожидаемой структурой

### 5. CI

- В workflow из Task 17 — отдельный job `integration`: services (или compose) + `npm run test:integration`

## Технические заметки

- **Границы:** LLM живьём не тестируем (квота GLM-тарифа, флаковость) — только фейковый транспорт; GitHub API — мок по fixtures; Ollama — мок (контракт тонкий, вес контейнера в CI неоправдан)
- Сетка маленькая: 5–10 сценариев на критичные контракты, не «покрытие»
- Юнит-тесты (Task 16) не зависят от Docker и остаются быстрыми — разделение glob'ов обязательно
- Тесты запускаются и локально, и в CI — один и тот же compose-файл
