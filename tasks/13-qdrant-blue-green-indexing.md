# Task 13 — Blue-green индексация Qdrant: теневая коллекция + атомарный switch через алиас

|                 |                                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Приоритет**   | 3 — после Task 12 (рефакторинг `application`, индексация станет пайплайном)                                                                       |
| **Зависимости** | Task 12, Task 14 (шов финализации Flows, пер-repo локи)                                                                                           |
| **Открывает**   | Zero-downtime смену схемы векторов/payload-индексов, мгновенный rollback синка, удаление sha-инкрементальности в пользу полной теневой пересборки |

## Контекст

Сейчас `repo-sync` индексирует в **ту же коллекцию**, из которой читает `analyze-pr`. ID чанка = uuidv5(`filename_contentHash`) — у изменившегося файла новый hash → новый ID, а старые чанки живут до финального `cleanupOldSyncData`. Итог: всё время индексации анализ видит **дубли изменённых файлов (старая + новая версии) и смесь старого/нового контекста**.

Решение — стратегия blue-green **внутри одного инстанса Qdrant** через нативные collection aliases:

- На репозиторий две физические коллекции: `code_<repo>_blue` и `code_<repo>_green`
- Публичное имя — **алиас** `code_<repo>`, всегда указывающий на активную коллекцию
- Индексация идёт в теневую (анализ её не видит), по завершении — атомарное переключение алиаса, старая коллекция удаляется

Ключевое свойство: для `analyze-pr` и контроллеров ничего не меняется — они продолжают работать с именем `code_<repo>`, которое теперь алиас. Вся blue-green-механика локализована в `modules/vectorstore` и пайплайне индексации.

## Объём работ

### 1. Нейминг и разрешение цвета

- `modules/vectorstore/qdrant.utils.ts`: парсинг/сборка имён — физическое `code_<repo>_<color>` ↔ публичный алиас `code_<repo>`
- Источник истины по активному цвету — **сам Qdrant** (`listAliases`), состояние в Redis не дублируем
- Если алиаса/коллекций нет (первый синк) — создать обе, алиас на `blue`, теневая — `green`

### 2. Расширение `modules/vectorstore/`

`qdrant.service.ts` + `qdrant.adapter.ts`:

- `resolveCollections(repoId)` → `{ active, shadow }` по текущему алиасу
- `switchAlias(repoId)` → атомарный `updateCollectionAliases` (переключить `code_<repo>` на теневую)
- `recreateShadow(repoId)` → drop + create теневой коллекции с payload-индексами (через существующий параметризованный `ensureCollection`)
- Порты: расширить `VectorStorePort` (после Task 12 — контракты пайплайна индексации) методами `resolveCollections` / `switchAlias` / `recreateShadow`

### 3. Пайплайн индексации (после Task 12 — `pipelines/indexing/`)

Новый флоу `repo-sync`:

1. `recreateShadow` — теневая пересоздаётся пустой (полная пересборка, без sha-инкрементальности `storedFilesMap` / `updateSyncIdForFile` / `cleanupOldSyncData`)
2. Полная индексация всех файлов в теневую
3. Успех → `switchAlias` (атомарно) → drop бывшей активной
4. Провал → активная не тронута, анализ продолжает работать на старых данных; теневая останется мусорной — не страшно, следующий синк начнётся с `recreateShadow`

- `sync_id` в payload оставляем для наблюдаемости, но механика очистки по нему уходит
- Оркестрация — BullMQ Flows из Task 14: `recreateShadow` и финальный `switchAlias` — в parent-джобе (шов финализации подготовлен в Task 14, п.3), пофайловая индексация — child-джобами в теневую коллекцию
- Глобальный loc `SyncStatusPort.isBusy()` не сохраняем — удаляется в Task 14; взаимоисключение синков одного репо — per-repo Redis-локи (Task 14), параллельные синки разных репо появляются там же

### 4. Кеш эмбеддингов документов (опциональная фаза)

Полная пересборка повторно эмбеддингит неизменившиеся чанки. Смягчить: кеш в Redis по hash контента чанка (по образцу существующего `EmbeddingCachePort` для запросов). Если объём фазы распухает — вынести в отдельную задачу.

### 5. Проверка прозрачности алиаса

- Гибридный поиск (RRF через Query API) и `getPoints` адресуются алиасу — убедиться, что всё работает без изменений на стороне `analyze-pr` / контроллеров
- `ensureCollection` при создании физической коллекции обязан ставить все payload-индексы — иначе после первого свича поиск по payload сломается

## Технические заметки

- Переключение алиаса в Qdrant атомарно — это и есть «мгновенный switch» вместо копирования инстанса; второй инстанс Qdrant не нужен
- Rollback-окно (держать старую коллекцию N минут для отката) — **опция**: в v1 просто drop, откат = повторный синк
- Будущий бонус (не в этой задаче): смена размерности векторов или payload-схемы без даунтайма — теневая коллекция создаётся с новой схемой
- `docker-compose` использует `qdrant/qdrant:latest` — alias API стабилен давно, но зафиксировать версию образа не помешает (отдельно от этой задачи)
- Вне задачи: snapshot API, Qdrant gRPC (Task 05; операции с алиасами внесены в его spike-чеклист)
