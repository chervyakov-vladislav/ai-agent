# Правила разработки модулей (src/modules/)

Все модули в директории `src/modules/` должны следовать единому архитектурному паттерну "Сервис-Адаптер" для обеспечения чистоты архитектуры и легкой подменяемости реализаций.

## Структура модуля

Типичный модуль должен состоять из следующих файлов:

- `[module].service.ts` — Основная логика и взаимодействие с внешними API.
- `[module].adapter.ts` — Адаптер, реализующий порты (интерфейсы) приложения.
- `[module].constants.ts` — Константы, специфичные для модуля.
- `[module].utils.ts` — Вспомогательные функции.
- `[module].validators.ts` — Схемы валидации (Zod).
- `[module].types.ts` — Внутренние типы модуля.

### Расширение структуры

Базовый набор — не потолок. Если в модуле выделяется отдельная ответственность, которая не помещается в существующие файлы (маппинг внешних данных в доменные типы, стратегии парсинга, шаблоны промптов, билдеры и т.п.), — **предложи пользователю** завести новый файл `[module].[роль].ts` (например, `github.mapper.ts`), а не молча раздувать `*.service.ts`.

- Одна роль = один файл: `*.mapper.ts`, `*.strategy.ts`, `*.prompt.ts`.
- Однотипные роли группируются в подпапку: `prompts/`, `strategies/` (примеры в коде: `llm-gemini/prompts/`, `ast-parser/strategies/`).
- Разовая функция на пару строк — сначала в `*.utils.ts`; отдельный файл заводить только при накоплении реального объёма.

## Правила и закономерности

1.  **Централизация логики (Service):**
    Вся основная логика, работа с внешними библиотеками и API-вызовы должны быть сосредоточены в файле `*.service.ts`. Функции сервиса должны быть максимально независимы от контекста приложения.

2.  **Реализация портов (Adapter):**
    Файл `*.adapter.ts` служит мостом между модулем и слоем приложения (`application/use-cases`).
    - Адаптер **обязан** имплементировать нужный Port (интерфейс), определенный в слое Use Case.
    - Адаптер делегирует выполнение задач соответствующим методам из `*.service.ts`.
    - Адаптер может выполнять маппинг данных из внутреннего формата модуля в формат, ожидаемый приложением.

3.  **Разделение ответственности:**
    - Не храните константы в файле сервиса — выносите их в `*.constants.ts`.
    - Сложные преобразования данных, не зависящие от состояния, выносите в `*.utils.ts`.
    - Валидацию данных (особенно ответов от внешних API) выносите в `*.validators.ts`.

4.  **Импорты:**
    - Адаптеры импортируют методы из своего сервиса через `import * as service from './module.service'`.
    - Приложение импортирует только адаптеры (через алиас `@modules/...`).
